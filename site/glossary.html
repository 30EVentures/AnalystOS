Hiring a role

How a problem becomes a piece of work.

Role
One of 73 entry-level white-collar jobs AnalystOS can do, such as FP&A analyst, paralegal or claims adjuster. Each role has its own focus and its own limits; its intake questions are the common ones plus its family's.
Family
A group of related roles, such as finance and modeling or legal, contracts and procurement. There are 13. Roles in a family share a delivery format and the same intake questions.
Engagement
One piece of work: the problem you describe, your answers to the role's questions, and the file you get back.
Intake questions
What a role asks before it starts: the decision the work supports, the deadline, who will read it, the materials, and questions specific to the family.
Acceptance
The check that every required question has an answer. Work starts only after it.
Worked example
A synthetic client's problem and a response run through the real checks, with no model call. Every role has one; it is what the role's sample is made from.
Sample
The file the homepage shows for a role, built from its worked example, in the role's own format. The client in it is not a real company.

How numbers are traced

Every number in the output has to come from somewhere you can check.

Figure
A number in the work, recorded with an id (F1, F2 and so on), a label, a value, a unit and where it comes from. The text carries no other numbers, apart from years and labels such as Q3, FY24 or Phase 2.
Figure tag
The small reference printed after each number, such as F3, so a reader can find its source in the sources table.
Client figure
A number taken from your own words. Its quote must appear in what you wrote, and the number in the quote must equal the figure.
Calculated figure
A number worked out from earlier figures by a named operation, such as a difference or a share. Code redoes the arithmetic before anything is drawn.
Labelled assumption
A number you did not give, marked as an assumption with its reason, so it is never mistaken for a fact.
Verifier
The code that checks the model's work before any file is drawn: quotes, arithmetic, units, stray numbers, and the role's own rules. Before it runs, code tidies mechanical slips that do not change what a reader is told, such as a quoted 7% stored as 0.07. The verifier itself changes nothing: it passes the work or refuses it.
Repair
When the verifier refuses the work, the model is told each problem in plain words and gets one more attempt. If that fails too, no file is made.
Fail closed
When a check cannot be completed, the answer is no, not yes. A file that cannot be re-checked is not delivered.
Spec digest
A fingerprint of the checked content, written into each file's properties, so the file can be tied back to exactly what was verified.

What you get back

Finished work in the format the role's work is read in.

Format
A Word memo for legal, research, audit, HR, insurance and financial crime; an Excel workbook for finance, accounting and data; a PowerPoint deck for consulting, content, sales and software.
Live formula
In a workbook, each calculated figure is an Excel formula over the inputs, so you can change an input and see the result move.
Work product
The role's own work, inside the file: a draft, register, case file, reconciliation, plan or draft code. 40 of the 73 roles deliver one or more.
Draft
Copy written for you to use, such as an email, a post or a notice. AnalystOS does not send it.
Register
A table of items to track, each with a rating, an owner, a status and an action.
Case file
The facts, the evidence and the open questions on one matter, ending in a question for the person who decides. It never decides.
Reconciliation
Two balances and the items that explain the difference between them. Code checks that the sides agree; any journal entries are proposals for approval.
Plan
Steps with when, who and how you will know each is done.
Draft code
A short piece of code labelled as not run or reviewed. Numbers inside code are the one thing the figure rules do not cover, and the file says so.
Placeholder
A detail in curly braces, such as {start date to confirm}, left for you to fill in because you did not give it. The worked examples use this convention; nothing yet checks that a draft does.

Who decides

Each role states what it may and may not do.

Boundary
What a role is allowed to do. Every role is one of three kinds: it delivers work only, it drafts for approval, or it prepares a decision for a qualified person.
Delivers work only
The role hands over analysis or a draft and acts on nothing.
Drafts for approval
The role prepares messages, entries or bookings for a named person to approve. AnalystOS itself sends, posts and pays nothing.
A qualified person decides
The role prepares the decision, and a named person, such as counsel, an underwriter or a compliance officer, makes it. The work says who.

For agents

The parts of the site made for software as well as people.

Agent caller
Software that hires a role through the API rather than a person using the website. It gets the same checks and the same limits.
Budget
What one hire may use, in model calls and output tokens. A caller can only narrow this server's limits, never widen them; asking for more is refused before any call. There is no money in it: no price has been set.
Receipt
A record of one hire: who the caller said it was, the role, the budget, the usage the model reported, and the fingerprint of the file delivered, or that nothing was. Receipts are not signed yet, so they are this server's account, not proof. See the hiring API guide.
Role catalog
Every role, its family, questions, format and limits, as JSON at /api/v2/catalog.
llms.txt
A short plain-text index of the site for language models, at /llms.txt.
API catalog
A machine-readable list of where each API and its documents live, at /.well-known/api-catalog.
Seal
A signed bundle for a report from the document-upload path, so someone who did not run AnalystOS can check it offline against a public key they pin. See the seal specification.
