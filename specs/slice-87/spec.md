# Slice 87 - a refusal-first conformance corpus for seal and audit-log verification (Flashy integration J1)

## Goal

The seal verifier and the audit-log verifier are tested by hand-written unit tests that share the
author's blind spots. A corpus is different: a data file of inputs and the verdict each must get,
with most of the cases being things that **must be refused**, runnable by any implementation in any
language through a one-JSON-object-per-line protocol. It is how a stranger's port proves it agrees
about what to reject, and how we find where our own verifiers are lenient.

The shape borrows the wire protocol of Flashy's `conformance-kit` (`{id,set,input}` in,
`{id,valid,codes}` out, four outcomes: agreed, disagreed, unanswered, unreadable). Nothing of
theirs is copied; the corpus, the generator and the adapter are ours.

- `conformance/seal-1.json`: generated by `tools/build_conformance_corpus.py` (never hand-edited).
  Five sets: `seal` (internally consistent), `seal-authentic` (signature under a key you pinned, or a
  published key file), `seal-content` (checked against the supplied text), `audit` (the hash-chained
  log verifies), `audit-authentic` (every line signed and verified under the pinned key). Each case is
  `{id, set, input, expect: {valid, codes?}, note}`. Expectations are written by hand in the
  generator, never computed by the code under test.
- `analystos/conformance.py`, run as `python -m analystos.conformance`: the line-protocol adapter
  (pattern of `analystos/aao/kit.py`). A verifier crash leaves the case **unanswered** (traceback on
  stderr) rather than being turned into a verdict.
- An in-process runner (`run_corpus`, `problems`) used by `tests/test_conformance_corpus.py`.
- Cases the current code gets wrong stay strict and carry a `known_gap`; the suite requires them to
  keep failing until the annotation is removed with the fix.

## Not in this slice

- Running Flashy's kit in the suite or vendoring any of their code (a one-off external cross-check is
  run by hand and reported in `docs/decisions.md`).
- Publishing the corpus under `site/` or on any URL.

## Done when

1. The corpus has at least 45 cases, at least 60% of them refusals, unique ids, and strict JSON
   (no `NaN`).
2. The suite fails if the runner executes zero cases, or any case is unanswered, unreadable or
   disagreed (outside an annotated known gap), or refusals fall under 60%.
3. Every case the brief names is present: valid and unsigned bundles, a pre-Slice-83 bundle, tampering
   of value, quote, key and root, swapped / foreign / wrongly-pinned signatures, malformed payloads and
   proofs, duplicate keys, exotic numbers and characters, oversized fields; and for the audit log valid,
   edited, deleted, reordered, inserted, tail-dropped (only detectable with `expected_head`),
   signature-stripped, legacy-only and empty logs.
4. The corpus file is current with its generator (`--check`), and the adapter answers over stdin.
5. Every bug the corpus exposes is either fixed in its own commit with a regression test or recorded
   in `docs/decisions.md` as an expected failure.
